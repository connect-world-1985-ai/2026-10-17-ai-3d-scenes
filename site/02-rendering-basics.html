Part II — Fundamentals

Render loop, scene graph and camera

Every real-time 3D scene, from a spinning cube to a city fly-over, runs the same three ideas: a loop that redraws the picture many times per second, a tree of objects whose positions are relative to their parents, and a virtual camera that turns 3D points into 2D pixels. If you know these three, you can read any agent-written Three.js file.

The render loop

A 3D page is an animation. About 60 times per second (or 120 on a high-refresh screen) the browser calls your function, you update the world, and you ask the GPU to draw it. In Three.js that is renderer.setAnimationLoop(fn), a wrapper around the browser's requestAnimationFrame.

const renderer = new THREE.WebGLRenderer({ antialias: true });
renderer.setPixelRatio(Math.min(devicePixelRatio, 2));   // cap: 3× phones melt
const clock = new THREE.Clock();
renderer.setAnimationLoop(() => {
  const dt = clock.getDelta();          // seconds since last frame
  boat.position.x += 4 * dt;            // 4 metres per second, at any frame rate
  renderer.render(scene, camera);
});

Two practical points Practice:

  • Browsers throttle hidden tabs. A loop that relies on wall-clock time will "jump" when you come back. Clamp dt (for example to 0.1 s).
  • Pixel ratio is a hidden cost multiplier. At devicePixelRatio 3, the GPU shades 9× the pixels of a ratio-1 canvas. Most production code caps it at 2. Inference (arithmetic)

The scene graph

A scene is a tree. Every object (Object3D) has a position, rotation and scale relative to its parent. Rotate a parent and all its children move with it. That is how you make a moon orbit a planet that orbits a star without any trigonometry: put the moon inside the planet, the planet inside an invisible "orbit" group, and spin the groups.

Under the hood each node stores a 4×4 matrix; the GPU receives the product of all matrices from the root down (the world matrix). Agents occasionally confuse local and world coordinates. A typical symptom is an object that is in the right place until its parent moves. The fix is getWorldPosition() or attach() instead of add(). Practice

Camera and projection

A perspective camera is defined by four numbers:

  • vertical field of view (degrees);
  • aspect ratio (canvas width ÷ height);
  • near and far clip distances.

Together they form a truncated pyramid, the frustum. Anything outside it is not drawn. The projection matrix squashes that pyramid into a cube, and the GPU maps the cube to pixels.

  • Field of view. 50–75° feels natural for first-person; 20–35° looks like a telephoto drone shot and flattens a city; above 90° looks like a fisheye.
  • Near and far set depth precision. The depth buffer has finite precision spread non-linearly between near and far. With near = 0.001 and far = 100000, distant surfaces flicker against each other: z-fighting. Raise near as far as you can (0.1–1 m for a walk-through). For planet-scale scenes, use logarithmicDepthBuffer: true. Practice
  • Orthographic cameras have no perspective: parallel lines stay parallel. Used for isometric cities, maps and shadow cameras.
  • Aspect must be updated on resize (camera.aspect = w/h; camera.updateProjectionMatrix()). A stretched, squashed scene is a classic agent bug.

Coordinates, units and handedness

  • Three.js is right-handed, Y up, and by convention 1 unit = 1 metre. glTF uses the same. Blender is Z up; its glTF exporter converts. Unreal uses centimetres and Z up. Unity is left-handed, Y up. Practice
  • Many "the model is huge or tiny" bugs are unit mismatches. Physical lighting, fog distances and camera speeds only look right at the correct scale. A person is ~1.7 m, a storey ~3 m, a city block 80–200 m.

What the GPU actually does

For each draw call the GPU runs a small program per vertex (the vertex shader, which moves points into screen space). It then rasterises triangles into fragments, roughly pixels, and runs a second program per fragment (the fragment shader, which computes the colour). Every material you use, even a built-in one, is ultimately a pair of these programs. Three.js writes them for you, and page 04 shows how to write your own.

Reading an agent's Three.js file in 30 seconds Look for these, in this order:
  • the renderer (settings, tone mapping);
  • the camera (FOV, near, far);
  • the lights or scene.environment;
  • the meshes (geometry + material);
  • the setAnimationLoop body (what changes over time);
  • the resize handler.
Almost every file follows this shape.
