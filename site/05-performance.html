Part II — Fundamentals

Performance: draw calls, instancing, LOD and culling

A city of 20,000 buildings can run at 60 frames per second, or at 4. Same buildings, same GPU: the difference is how many times the CPU has to ask the GPU to draw something. This page explains the budget every frame lives inside, and the four standard tricks that keep big scenes smooth.

Why performance is the whole game

  • The budget. At 60 fps you have 16.7 ms per frame for everything: JavaScript, physics, draw calls and GPU work. At 120 Hz, 8.3 ms. Miss it and the scene stutters, and in first-person, stutter feels much worse than low detail.
  • Laptops throttle. A scene that runs at 60 fps for 30 seconds can drop once the GPU heats up. Integrated GPUs share memory bandwidth with the CPU. Practice
  • Agents rarely notice. A headless test browser often uses a software renderer and reports whatever frame rate it gets. Benchmarks show the problem is usually not the agent's GPU code but CPU-side overhead. In the AA-3D benchmark, every model's median frame took under 1.3 ms of GPU time on the test machine. Those were relatively light scenes. Verified

Draw calls: the CPU bottleneck

Each separate mesh with its own material usually costs at least one draw call. That is a command from JavaScript, through the browser's graphics layer (ANGLE on Windows translates WebGL to Direct3D 11), to the driver. Each call costs CPU time no matter how small the object is. Common rules of thumb Practice:

  • 50–100 draw calls for mobile (Three.js community guidance, McCurdy 2021);
  • 100–200 on low-end mobile, and thousands on desktop (PlayCanvas optimisation guidelines).

These numbers vary widely by device. Treat them as orders of magnitude, not limits.

Three.js shows the count in renderer.info.render.calls. Every demo in this guide prints it in the HUD.

Trick 1: instancing

If 10,000 objects share the same geometry and material (buildings, trees, cars, windows, grass blades), draw them in one call with a per-instance transform matrix and colour. In Three.js: new THREE.InstancedMesh(geometry, material, count), then setMatrixAt(i, m) and setColorAt(i, c). The GPU loops over the instances itself.

Related tools:

  • Merging (BufferGeometryUtils.mergeGeometries): bake many static meshes into one. It is cheap to draw but cannot move objects individually.
  • BatchedMesh: one call for different geometries that share a material, with per-object culling. See the webgl_batch_lod_bvh example. Verified

Try it: separate meshes vs one InstancedMesh

Set 20,000 objects and switch between the two modes. Watch the draw calls and CPU time in render() lines in the HUD. The triangle count is identical; only the number of calls changes. Building 20,000 separate meshes also takes a noticeable moment after you change the slider.

In separate mode each object also gets its own material, as naive agent code often does, so nothing can be batched. Your numbers depend on your CPU, GPU and browser.

Trick 2: level of detail (LOD)

A building 2 km away covers a few pixels; drawing its 5,000 triangles is waste. LOD swaps in simpler versions with distance: Three.js's THREE.LOD object, the official webgl_lod example, or automatic simplification with meshoptimizer. At the far end, distant buildings become flat "impostor" cards or merge into one block per district. Unreal's Nanite automates this with virtualised geometry; the web has nothing equivalent built in. Trick 3: culling

  • Frustum culling: skip objects outside the camera's view pyramid. Three.js does it automatically per object (frustumCulled = true by default). It tests each object's bounding sphere. Verified
  • Gotcha: an InstancedMesh is one object. If its bounding sphere is computed wrongly (for example after you move instances), the whole city can disappear at certain angles. Call computeBoundingSphere() after updating instances, or set frustumCulled = false.
  • Occlusion culling: skip things hidden behind other things. That is very effective in street-level city views, but not built into Three.js. Engines like Unreal do it automatically.
  • Distance culling plus fog: let fog swallow the far plane, and do not draw beyond it. The cheapest trick of all.

Trick 4: spend pixels wisely

  • Pixel ratio. Cap setPixelRatio at 1.5–2. A 4K laptop panel at ratio 2 means shading 8 million pixels per frame.
  • Post-processing passes each touch every pixel, often several times. Bloom at half or quarter resolution looks the same. The official Three.js WebGPU city example runs bloom at quarter resolution. Verified
  • Shadow maps. Every shadow-casting light re-renders the scene. One sun with a 2048² map is the norm; avoid shadowed point lights.
  • Overdraw. Transparent things (foliage cards, particles, glass) are drawn back to front and cannot skip hidden pixels. Big transparent planes are expensive.
  • Shader compile time. The first frame can take seconds while the driver compiles shaders. The night-street project measured 34.9 s and 39.4 s to first frame on an RTX 4060 with a cold cache; over 95% of that was shader compilation, not geometry or textures. Verified (repo README, 2026-10-17)
