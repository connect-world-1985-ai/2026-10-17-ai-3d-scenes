Part IV — Assets and agents

How the agent works: knowledge, iteration, and eyes

A language model writing 3D code is working blind unless someone shows it the result. The best evidence available in October 2026 points one way: the agents that produce the best scenes are the ones that look at their own output early and often. This page covers what the model knows already, how it sees, what typically breaks, and which tools and MCP servers give it eyes and hands.

One-shot knowledge vs iteration

A model "knows" Three.js the way you know a language you read a lot: it has seen thousands of examples, including the official ocean, FPS and bloom examples, ShaderToy classics and tutorials. So a first attempt usually contains the right building blocks. But:

  • It cannot predict pixels. Whether fog matches the sky, whether a shader is too bright, whether the camera clips a tower: none of that is visible from code.
  • Its knowledge is mixed across versions. Three.js removed or renamed many APIs between r125 and r186; the model blends them (failure table below).
  • Taste needs a reference. "Make it look like a photo taken at 11 PM on a phone" works much better when the agent can compare its render against that target.

The AA-3D benchmark (Artificial Analysis, 2026-10-12) measured this directly. Each model ran as an agent in an offline sandbox with Blender, Rapier physics, Python, a headless browser and a CC0 asset library, for up to 3 hours or 250 turns per scene, across 55 tasks. Verified

  • The top five models first looked at an image of their own scene after a median of 10–13 turns; models ranked 14th–20th waited until turn 15–40.
  • Across the 19 image-capable models, looking early tracked rank closely (Spearman 0.82). "How often a model looks matters less than when."
  • Agents spent 82% of their tool time testing the page in a browser (screenshots and error checks); writing code was 6% of tool time.
  • Two text-only models (GLM-5.3, Nemotron 3 Ultra) built every scene without ever seeing it. GLM-5.3 fell furthest below the score its general intelligence predicts; its sibling GLM-5.3-Flash, which can view images, scored 149 Elo higher.
  • Output tokens and turn counts did not predict quality. The number of interactive UI controls did (Pearson 0.90).

These are correlations from one benchmark, not proof of cause. Inference

The iteration loop

  1. Console first. Errors are text: cheap and exact. One example from the night-street project: its whole audio system was silent "from the day it was written" because a ConvolverNode threw, and "the error was in the page console the whole time". Verified
  2. Screenshots from fixed poses. Good projects add URL parameters so a script can reproduce a shot. The LAAS world demo uses ?cam=, ?shot=, ?freeze=1 and ?T=hours, plus a scripted 90-second flythrough. Verified
  3. Metrics in the picture. An on-screen HUD with FPS and draw calls means every screenshot carries performance data (all demos in this guide do this).
  4. Vision review against the brief. night-street used a separate "blind critic" subagent that saw only renders and judged them against real photography. Verified

That is exactly how this guide's demos were checked: a Playwright script opened each page from file:// in headless Edge, collected console errors, screenshotted each demo and printed its HUD. That loop caught a city demo washed out to white by bloom, a camera clipping into towers, and a HUD that under-counted draw calls. None of those were visible in the code. Verified (this project)

The headless GPU problem

Headless browsers often have no GPU, so WebGL needs a software renderer:

  • Chromium's automatic SwiftShader fallback is deprecated. To opt in for testing, pass --enable-unsafe-swiftshader; on Windows the replacement fallback is WARP (D3D11). Verified (Chromium docs, blink-dev)
  • Software-rendered FPS numbers say nothing about real performance. A benchmark that reports 2–28 fps from headless Chrome is measuring a CPU rasteriser. AA-3D instead reports GPU time per frame on a test machine. Inference
  • Headless WebGPU is harder: it needs full Chromium (not the headless shell), Vulkan flags or a real GPU, and a secure context (http://localhost, not file:// or about:blank). Practice
  • Log the unmasked renderer (WEBGL_debug_renderer_info) so the agent knows which GPU it measured on.

Skills and rules

Several community "skill" packs teach agents Three.js: CloudAI-X/threejs-skills (3,588 stars, no licence listed), dgreenheck/webgpu-claude-skill (1,252 stars), R3F skill packs and others. Verified Evidence that they help is thin. I found no controlled study. The one detailed account I found, night-street's own survey, called the installed skills "flat API catalogues with no measurement", useful for "what an API is" but "no help … with what number to put in it". Its most useful source was the previous project's code comments. Verified (one author's opinion) My reading: a short project rules file (pinned versions, banned APIs, the test loop, asset policy) is cheaper and more reliable than a big skill pack. Inference

Security: these servers execute code by designBlender MCP runs model-written Python with full access. Epic's Unreal MCP has no authentication, and "localhost is not a trust boundary": any same-user process can connect. Anything the agent reads (asset descriptions, web pages, tool descriptions) can try to steer it. Use a throwaway project under version control, keep secrets out of the environment, and prefer per-call approval over "skip permissions" modes. Verified (READMEs, CVE record) / Practice (mitigations)

Two styles of engine automation:

  • Headless scripts, no MCP: blender -b --python build.py, godot --headless --script, UnrealEditor … -run=pythonscript, Unity -batchmode -executeMethod. You read the output PNG. Easier to secure and reproduce.
  • Live editor over MCP: more interactive, more powerful, more risk.

Inference

Practical rules for your own runs

  1. Pin versions in the first prompt and name the APIs that are banned.
  2. Require a test script from turn one: open the page, fail on any console error, screenshot from 2–3 fixed poses.
  3. Ask for a HUD with FPS and draw calls, and URL parameters for camera, time and seed.
  4. Give a visual target: reference photos, or a precise description of light and mood.
  5. Review the screenshots yourself every few iterations; the agent's taste is not yours.
  6. Stop it from "fixing" by deleting features: list the must-haves.
